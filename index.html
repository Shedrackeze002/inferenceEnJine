One deployment, four working layers

Each layer runs on your infrastructure when we deliver it. Every layer has evaluations and a runbook.

Knowledge layer

Your contracts, wikis, tickets, and reports become an index you can query. The index runs on your infrastructure. Claude reads the retrieved context and answers with citations to your sources. Accuracy is measured with questions your team writes, before anyone trusts the system.

RetrievalClaude APIBuilt-in evals

Automation layer

Workflows in n8n move work between the tools your team runs. One workflow can pull records, apply rules, write outputs, and alert a named person when a check fails. Claude does the steps that need reading and judgment. Deterministic gates, retries, and audit trails do the rest.

n8nClaude for judgment stepsAudit trails

Model layer

Open models, fine-tuned on your data, do the high-volume tasks with known steps. Training uses LoRA and QLoRA on one consumer GPU. Hard reasoning stays on Claude. An evaluation harness routes each task to the correct layer. The routing decision uses measured accuracy.

LoRA / QLoRAClaude for hard reasoningEval harnesses

Cost layer

The audit gives your cost numbers before the build starts. Some tasks need a frontier model. Other tasks run cheaper on quantized open models (int8, 4-bit) on machines you own, including Apple Silicon. The goal: minimum API spend on reasoning, and self-hosted serving for all other work.

Built on Claude

What Claude does in every deployment, and what stays on your hardware.

  • Reasoning engine in the knowledge layer Claude reads the retrieved context and answers with citations from your index.
  • Judgment steps in the automation layer Document parsing, request classification, and drafting run as Claude API calls in the workflow.
  • Agent tooling for setup and QA The Claude agents that build a deployment also verify it. The verification includes harness design, evaluation runs, and pre-launch checks.

What stays on your hardware

  • Document ingestion and chunking
  • Embeddings and the retrieval index
  • Quantized open models (int8 / 4-bit) for high-volume tasks
  • The serving layer, behind your network

Your documents stay inside your deployment. Raw data never leaves it.

How a deployment runs

Every engagement has a fixed scope of 4 to 8 weeks. Every checkpoint leaves a working system.

Week 1

Audit

In the audit, I map your documents, tools, and current spend. Then I write a one-page plan with the architecture, the hardware, the cost math, and the model routing. You approve the math before the build starts.

Weeks 2 to 6

Deploy

I build the system in code you can read. The build includes pipelines, indexes, evaluation harnesses, and deploy scripts.

  • Weekly checkpoint with a running system
  • Evals measured on your data, not toy data
  • You can stop at any checkpoint and keep the work.
Final week

Handover

I write the documentation and runbooks. I train the person who operates the system.

  • You see the operating cost before you pay it.

Proof, not claims

Three tracks of prior work. The numbers are measured. You can inspect the artifacts.

Native inference engines

I built C + Metal inference engines on Apple Silicon. The engines do not use PyTorch. On a 48 GB Mac, int8 quantization cut model memory from 36.4 GB to 25.9 GB. 4-bit quantization cut it to about 19 GB. Decode speed went from 23 to 37 tokens per second. These numbers turn memory limits into a planned decision.

36.4 → 25.9 GB (int8) ~19 GB (4-bit) 23 → 37 tok/s decode

Fine-tuning under constraint

I fine-tuned open vision and language models under hard memory limits. The training used gradient checkpointing, mixed precision, and batch choices. It ran on one consumer GPU. A BERT fine-tune runs as a public demo with 90.7% accuracy. An internal model gets the same treatment: measured accuracy on memory you can afford.
